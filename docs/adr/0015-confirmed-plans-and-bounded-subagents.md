# ADR-0015：版本化 Plan 模式与有界子 Agent

状态：Accepted

日期：2026-09-13

## 背景与授权

产品负责人明确要求用户可切换 Plan 模式，Agent 先列计划，用户明确确认后调用子 Agent 执行。此前路线图暂缓多 Agent，AGENTS.md P1.9、P3.2、P3.3 要求固定单 Agent Baseline 与收益证据，P3.4 优先首个包装产品闭环。本次将**确认计划后的有界子任务执行**提前纳入当前闭环；风险是模型调用成本和恢复状态增加。范围仅为本 ADR 所述的顺序、独立上下文子任务，其他多 Agent 平台能力仍暂缓。

## 决定

- 用户在工作台选择“直接执行”或“Plan”。Plan 模式的普通消息、重试及后台 Conversation Worker 均不能绕过计划 API 执行；自然语言“同意”不构成确认。
- 模型以只读工具生成 `PlanSpec`：摘要和 1–4 个独立子任务，每项包含目标及工具白名单。Host 校验结构、大小和工具名。失败或工具拒绝不会形成可确认计划。
- 计划及上下文按版本保存。确认命令绑定最新版本与状态修订号，要求显式 `confirmed: true`，记录操作者及时间。会话或附件索引变化时必须重新规划。
- Host 在确认后将子任务逐个交给同一 `AgentRuntimePort`。每个子任务有独立、确定性的 Session ID、目标、工具范围和结果；不会继承父 Agent 或兄弟 Agent 的推理消息。
- 子 Agent 不具备派生、后台任务、定时任务或自动发布工具。文件读写范围沿用本机用户已有策略；每次写入/删除仍需独立审批。计划确认不是文件操作审批。
- 每个子任务输出结构化摘要、证据与限制；这些是未验证的模型报告，不会修改权威 Fact 或成为生产就绪文件。Host 按计划顺序展示结果，不调用额外 Judge 或汇总 Agent。

## 分层与持久化

`src/enterprise/agentPlan.ts` 定义行业无关契约；`server/enterprise/agentPlanWorkflow.ts` 管理模式、计划确认、预算、派发和结果；包装指令在应用 Host 装配时传入。Core 不识别 Plan、Artifact 或子 Agent 的业务状态。

`AgentPlanStore` 使用 Node 内置 SQLite，以追加事件保存每次状态版本，按 tenant/workspace/conversation 隔离，事务内检查状态修订号和命令摘要。同一用户命令重放不重复变更，复用 ID 但更改内容会被拒绝。每个计划版本及其子任务结果构成结构化、版本化的工作流交付记录；历史事件和原始计划不会被覆盖。

确认后的持久状态也是投递意图。现有 `StageJobQueue`/`StageJobScheduler` 根据确定性 Job ID 补投，使用原有租约、心跳、取消和失效 Worker 防护。一个 Job 按执行片继续，不引入新队列或多 Agent 总线。

## 状态与权限

主要路径：`planning → awaiting_confirmation → queued → running → completed`。运行可暂停到 `paused`，显式恢复后重新排队。失败记录分类；可重试的 Provider 故障允许恢复。无效输出、来源变化、工具失败等需用户重新规划。取消和替代后的版本不能恢复。

修改任务生成新版本会替代待确认、暂停或失败的旧版本。切换到直接执行会使待确认计划失效。运行时先暂停再切换。关闭浏览器不会自动取消已确认任务；删除会话会通过持久化删除标记和队列清理取消执行，保留审计记录。

每份计划生命周期最多 16 次 Runtime 执行片（包括规划、失败与恢复）；每片最多 4 次 Loop 迭代、8 次工具执行、12,000 个输入 Token，60 秒超时。Provider 自身输出上限和现有重试/压缩逻辑继续生效，这不是精确美元账单上限。取消、重新排队不会重置计划预算。Runtime request limits 只能收紧已有运行上限。

## 恢复与失败边界

- 已提交的子任务结果直接跳过，不再次调用模型。
- 子 Session 和完成 Trace 已保存、结果事件尚未提交时，恢复该完成结果。
- Session 已写入而完成 Trace 缺失时停止，报告 `plan_completion_evidence_missing`；不重跑工具来猜测此前是否成功。
- 工具非成功事件、无效结构化输出或来源变化不能被模型的“完成”文案覆盖。
- 文件操作沿用稳定幂等键、执行账本与哈希版本检查；不承诺无法判定的外部副作用会被自动修复。
- 不做嵌套子 Agent、依赖图调度、并行写入或自动合并冲突。同一计划的子任务应独立；有前后依赖的目标应作为单个子任务处理。

## 固定验证与替代方案

`npm run eval:plan` 使用固定 Provider、相同任务及运行限制，对比单 Agent 与两个独立子 Agent。固定场景中：单 Agent 1 次模型调用，规划加子 Agent 3 次；子任务上下文从 1 个共享执行上下文变成 2 个独立上下文，确认前执行数为 0。

该评测证明了隔离和确认行为，代价是额外调用；没有真实模型质量、速度或用户价值收益结论。回归测试覆盖来源与版本失效、租户、幂等、暂停、删除、预算、恢复和权限。HTTP 产品 fixture 覆盖真实 Host/Provider Adapter/Queue/结果读取链路。

纯 Prompt 规划不能保证只读和审批，因此不采用。任意 `spawn_agent` Tool 会把权限、数量和递归边界交给模型，因此本切片采用已确认计划的 Host 派发。新并行策略需要独立评测和后续 ADR。

## 迁移与退出

原会话默认直接执行。数据库新增在现有 Agent 数据目录的 `plans.sqlite`，不迁移旧会话、审批或文件。更名兼容的 `BLACKX_*` 配置继续适用。

若真实包装任务试用显示子任务成本或返工高于收益，用户可切回直接执行；停止新增 Plan 任务并保留历史记录。进一步扩大子 Agent 数量、权限或并行度前，必须补充真实任务评测，不能将本固定 fixture 当成性能收益证据。
