# Packx 开发者参与与项目展示指南

日期：2026-09-13  
状态：定位与执行方案；演示、社区入口和招募结果尚待实施验证。

本指南面向项目维护者，说明如何让其他开发者看懂、运行并参与 Packx。它不是已经完成的社区建设报告，也不替代 [AGENTS.md](../AGENTS.md)、[架构原则](architecture/principles.md)和[产品路线图](roadmap.md)。

## 1. 项目定位

统一产品名称为 **Packx**，原名 Blackx。对外介绍采用：

> Packx 是一个用 TypeScript 构建的开源包装行业 Agent 工作台，探索如何让 Agent 任务具备可追溯的事实、受控工具、版本化交付物、审批与中断恢复。当前以包装售前需求整理作为具体应用场景。

英文短介绍：

> Packx is an open-source TypeScript agent workspace for packaging presales, built around source-backed facts, controlled tools, versioned deliverables, approvals, and recovery.

包装行业提供明确用户和任务；Agent 与工作流工程提供开发者可以深入研究和贡献的技术问题。产品范围继续限定包装，底层 Core 和 Enterprise Layer 保持行业无关。更名不意味着扩展产品范围、发布独立 SDK 或完成生产 SaaS。

兼容性决定见 [D13](project-decisions.md#d13产品更名为-packx)：现有环境变量、数据目录、内部标识和 GitHub 仓库地址保持可用，历史证据保留原名。

## 2. 当前基础与待补入口

本轮仓库检查确认存在：

- 中英文 README、MIT 许可证、Node.js 24.14.0 与 npm lockfile 基线。
- `npm run dev:fixture` 免 API Key 体验入口，使用固定回复，完整流程依赖 macOS 原生读取器。
- Agent Core、工作流、事实、Artifact、审批与事件实现，以及离线测试和评测入口。
- `src/enterprise/proposalRunEngine.test.ts` 中的版本审批、上游事实变更和状态恢复测试案例。

这些是可检查的工程资产；某个命令存在不代表在任意平台或任意 Provider 上验证通过。真实包装目标用户价值仍需按路线图补验。

后续需要建立：短贡献指南、Issue/PR 模板、自动检查、核实过的入门任务、演示素材和首次贡献反馈流程。本次只记录这些计划，不创建招募 Issue、不发布内容，也不将候选任务描述为已经确认的缺陷。

## 3. README 与首屏叙事

首页先回答三个问题：解决什么问题、有什么能运行的证据、访问者能从哪里参与。

建议开场：

> Agent 能生成一份包装需求单。但客户修改数量后，旧需求单还有效吗？旧审批还能继续使用吗？执行过程中程序退出，又应该从哪里恢复？Packx 围绕这些问题构建可运行、可阅读、可参与的 Agent 工作台。

建议结构：具体问题 → 演示 → 快速运行 → 核心机制 → 贡献入口 → 当前边界。

准备好实际目标后再增加三个入口：

1. **体验工作台**：现有 fixture 启动说明，明确固定回复、平台和临时数据清理行为。
2. **理解实现**：一条请求从 UI 到 API、Runtime、工具和工作流的源码导读。
3. **参与贡献**：维护者已经核实范围和验收条件的任务列表。

保留完整配置和故障排查，通过链接逐层展开。对外品牌统一为 Packx；技术兼容标识和真实仓库 URL 按实际值展示，不能为视觉统一写出不存在的地址。

## 4. 演示设计：变化和失败发生之后

准备一段约 90 秒的演示，使用合成包装资料，覆盖以下流程：

| 步骤 | 展示内容 | 开发者关注点 |
| --- | --- | --- |
| 输入客户资料 | 草稿保留来源，标出缺失或待确认信息 | 事实与模型建议分离 |
| 确认并审批 | 生成具体版本，审批关联该版本 | 版本约束和状态转换 |
| 客户修改数量 | 旧交付物过期，旧审批失效 | 依赖追踪 |
| 中断后恢复 | 从持久化状态继续处理 | 恢复依据与重复执行控制 |

录制前逐步验证当前 UI 支持的链路。仅有测试覆盖的机制，用测试或事件记录呈现并注明范围；不得把合成资料说成真实客户验收，也不得把 fixture 回复说成实时模型推理。真实 Provider 演示与离线机制演示分别标注。

产出可复用为 README 动图、短视频和源码文章。验收要求是每个演示步骤都有可复现命令或操作记录，失败时停止录制并记录缺口，不以剪辑掩盖未实现功能。

## 5. 首批贡献者与参与路径

| 人群 | 参与动机 | 合适入口 |
| --- | --- | --- |
| 学习 Agent 工程的 TypeScript 开发者 | 理解完整请求和失败路径 | 源码导读、离线案例、评测 |
| React 与交互开发者 | 改善复杂执行状态的可理解性 | 单个审批交互、文件预览、错误提示、无障碍问题 |
| 关注可靠性与工具安全的开发者 | 解决有验收依据的工程问题 | 恢复、重复执行、文档解析边界与权限回归 |
| 了解包装业务的参与者 | 让需求单更贴近实际交付 | 授权且脱敏的案例、字段解释、可用性反馈 |

普通代码贡献不要求预先掌握包装知识。业务字段和生产约束的修改仍须权威资料或人工确认。安全和恢复任务由维护者先确定边界，不作为无人指导的新手探索任务。

## 6. 入门任务的准备标准

先筛选约五个小任务，逐个核实缺口。每个 Issue 写明：

- 用户问题与复现步骤。
- 已有代码入口和相关测试。
- 预期改动范围及明确不在本任务内的内容。
- 验收命令、预期结果、平台要求和是否需要外部模型。
- 维护者已完成的调查，以及认领和获得反馈的方式。

候选任务包括：干净环境安装走查、文档状态同步、单个组件无障碍修复、一篇英文源码导读、一个未覆盖的文档读取边界 fixture。重复执行或恢复案例更适合作为后续贡献。

候选项必须先复现或确认文档缺口，才能发布为工作项。跨平台沙箱、整个恢复系统、新 Provider 等工作不能标成 `good first issue`。已解决的问题不要为了凑数量继续开放。

## 7. 贡献指南和协作反馈

后续 `CONTRIBUTING.md` 应保持简短，首先告诉新人不必理解整个系统，随后提供按任务阅读的路径；修改架构与实现前仍需阅读 AGENTS.md。

至少覆盖运行和验证命令、目录职责、PR 流程、ADR 条件和维护者反馈方式。小范围修复可以直接提 PR；大改动先在 Issue 明确范围。维护者设定自己能兑现的首次响应时间，并在延迟时说明原因。

完整本地体验当前以 macOS 为基线。分别验证其他平台能够完成哪些文档、前端或离线测试任务，再公布对应贡献路径，不提前承诺跨平台支持。

自动检查应复用已有命令并按平台安排。在线模型评测独立运行，不要求新人提交密钥或为常规 PR 支付模型费用。合并要求继续遵循项目完成定义。

GitHub 的开源社区指南建议通过清晰贡献流程、适合新人的任务和积极反馈降低参与门槛：[Building Welcoming Communities](https://opensource.guide/building-community/)。这里将其落实为可验收的小任务和可兑现的维护者响应。

## 8. 内容与招募

每篇内容聚焦一个已有技术问题，给出例子、代码入口和验证方法：

- 客户改了数量，为什么 Agent 的旧审批必须失效？
- Agent 结束回复之后，业务任务真的完成了吗？
- 不调用真实模型，如何测试 Agent 的失败路径？
- 一次 Agent 文件写入，从提议到人工批准经过了什么？

文章结尾链接到已准备好的具体任务。先在维护者熟悉的开发者社区小范围发布，再根据反馈补英文版本；发布和邀请需由维护者执行或明确授权。

招募文案草案：

> 一起把包装 Agent 的审批、恢复与交付做扎实。
>
> Packx 是一个基于 TypeScript 的开源本地 Agent 工作台，当前服务包装售前需求整理。我们围绕事实来源、受控工具、版本化交付物和中断恢复构建可运行的工程实现。
>
> 欢迎对 Agent 工程、React 交互和可靠性测试感兴趣的开发者参与。可以从离线案例、单个 UI 问题或文档导读开始，无需先掌握包装行业知识。项目仍处于工程原型阶段，当前完整本地流程以 macOS 为基线。

## 9. 四周执行实验

以下为相对执行周次，不是已承诺的发布日期。维护者负责范围核实、评审和事实准确性。

| 阶段 | 产出 | 验收与停止条件 |
| --- | --- | --- |
| 第 1 周：准备入口 | README 首屏、贡献指南、五个核实过的小任务、协作模板 | 陌生开发者能找到运行入口和一个可认领任务；安装阻塞时先修复 |
| 第 2 周：展示机制 | 一段演示、一篇源码文章 | 每步都有验证依据；UI 不支持的部分明确展示为测试证据 |
| 第 3 周：邀请试用 | 少量目标开发者完成上手走查 | 记录平台、阻塞、理解困难和选题原因；优先处理重复阻塞 |
| 第 4 周：改善留存 | 修复主要阻塞、评审首批贡献、公开致谢 | 观察贡献是否完成、是否有人愿意继续；无反馈时调整入口与任务 |

观察指标：

- 独立启动成功率：在记录的平台和基线上，成功人数 / 实际尝试人数。
- 首次有效贡献耗时：从开始上手到获得维护者接受的代码、文档或可复现问题。
- 首次响应时间：从 Issue/PR 提交到维护者有效回复。
- 再次参与人数：完成首次参与后，再次提交或认领具体工作的独立参与者。

首轮可以设定“找到三位能独立运行、完成具体贡献并愿意继续交流的开发者”为实验目标。它不是增长预测；Star 数不能替代参与体验和真实用户价值证据。

## 10. 实施顺序与范围

先完成 README 首屏、贡献指南、核实过的小任务和一个可验证演示，再扩展传播。保持包装产品闭环优先，遵循路线图的安全和真实用户验证 Gate。社区吸引力不构成增加多 Agent、插件市场、自我修改或新行业入口的理由。

本次交付为 Packx 品牌更名和本指南入库。后续工作逐项记录实施结果、验证日期与未解决边界，避免将计划直接更新为“已完成”。
